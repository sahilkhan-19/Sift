================================================================
 SIFT — PROJECT ARCHITECTURE
 Local-first RAG (Retrieval-Augmented Generation) tool for PDFs
================================================================

1. OVERVIEW
------------------------------------------------------------
Sift is a local-first RAG command-line application for processing and querying PDF documents.
Users select a PDF via a native OS file dialog, choose embedding and LLM preferences, and ask
questions against the document. Answers are generated strictly from retrieved PDF chunks using
locally hosted LLM models. Sift runs entirely on the host machine with zero external API calls,
managing PyTorch GPU/CPU dependencies dynamically.


2. TECH STACK & DEPENDENCIES
------------------------------------------------------------
- Language & Runtime   : Python >=3.12, <3.14
- Package Manager      : uv (fast Python package installer and virtualenv manager)
- Standalone Executable: PyInstaller (compiles sift_exe.py into Sift.exe)
- Workflow Engine      : LangGraph (StateGraph finite state machine)
- PDF Parsing          : PyMuPDF (pymupdf)
- Text Chunking        : LangChain RecursiveCharacterTextSplitter
- Embedding Models     : HuggingFace BGE models (BAAI/bge-small-en-v1.5 / BAAI/bge-m3)
- Vector Store         : Qdrant (local embedded disk instance at ./qdrant_db)
- LLM Runtime          : Ollama (local server via langchain-ollama / ollama Python client)
- UI & Dialogs         : tkinter (native OS file dialog), Rich (terminal styling, spinners, progress bars)


3. DIRECTORY & FILE STRUCTURE
------------------------------------------------------------
.
├── Sift.exe           — Optional pre-compiled binary wrapper generated by PyInstaller.
├── Sift.spec          — PyInstaller configuration spec.
├── build_exe.bat      — Windows batch script to build Sift.exe via PyInstaller.
├── sift_exe.py        — Executable entry point. Ensures uv is installed, runs `uv sync`
│                        on first startup, and executes `uv run launcher.py`.
├── launcher.py        — Hardware calibration layer. Checks for NVIDIA GPU via `nvidia-smi`,
│                        validates active PyTorch build, installs matching CPU/CUDA wheels
│                        silently via uv, and restarts application into main.py.
├── main.py            — Application core. Implements PDF selection, LangGraph pipeline,
│                        Qdrant indexing, Ollama interaction, and session lifecycle.
├── ui.py              — Centralized Rich UI module. Custom theme, formatted tag prefixes,
│                        progress bars, status spinners, and ASCII banners.
├── pyproject.toml     — Project definition, dependency versions, and custom uv PyTorch index
│                        sources (pytorch-cpu / pytorch-cu130).
├── uv.lock            — Dependency lockfile.
└── qdrant_db/         — Transient directory created during indexing to store Qdrant vector data;
                         automatically deleted upon session cleanup.

5. DETAILED WORKFLOW SPECIFICATIONS
------------------------------------------------------------

A. Entry Point & Hardware Calibration (sift_exe.py & launcher.py)
   1. `sift_exe.py`:
      - Resolves project root directory.
      - Verifies `uv` CLI executable exists on PATH.
      - If `.venv` does not exist, triggers `uv sync` to bootstrap the virtual environment.
      - Executes `uv run launcher.py`.
   2. `launcher.py`:
      - Runs `nvidia-smi` to check for an NVIDIA GPU and extract CUDA driver version.
      - If GPU is present:
        - Inspects active PyTorch installation via `check_pytorch()`.
        - If CUDA PyTorch is already functional, launches `main.py --device cuda`.
        - If PyTorch is CPU-only, prompts user to select [1] CPU or [2] GPU. Re-installs
          PyTorch from either `https://download.pytorch.org/whl/cpu` or
          `https://download.pytorch.org/whl/cu130` using `uv pip install`, then restarts as
          `main.py --device <cpu|cuda>`.
      - If GPU is not present:
        - Installs CPU PyTorch build if necessary and restarts as `main.py --device cpu`.

B. PDF File-Picker Flow (main.py: pick_pdf)
   - Initializes a hidden `tkinter.Tk()` window (`root.withdraw()`).
   - Applies `-topmost` window attribute to bring dialog above current shell windows.
   - Triggers `filedialog.askopenfilename(filetypes=[("PDF files", "*.pdf")])`.
   - Validates selected path: checks non-empty input, filesystem existence, and `.pdf` extension.
   - If invalid or cancelled by user, application logs warning and terminates gracefully.

C. Indexing Pipeline (main.py: index_node)
   - Page Extraction: Opens PDF via PyMuPDF (`pymupdf.open`).
   - Dynamic Batching Strategy:
     - <= 100 pages : Entire document processed at once (`batch_size = None`).
     - 101-300 pages: Batch size = 30 pages/batch.
     - > 300 pages  : Batch size = 50 pages/batch.
   - Text Chunking: `RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200)`.
   - Embeddings: HuggingFaceEmbeddings assigned explicitly to target hardware (`cpu` or `cuda`).
   - Storage: Generates vector representations and writes to local Qdrant instance (`./qdrant_db`).
     Large files stream page batches with live progress updates using Rich `Progress`.

D. Retrieval & Answer Generation Flow (main.py: retrieve_node & generate_answer_node)
   - Performance Tiers:
     1. qwen2.5:7b   (Best Performance)
     2. phi3.5       (Performance)
     3. llama3.2     (Average)
     4. llama3.2:1b  (Quick)
   - Automated Pulling: Checks local Ollama catalog via `ollama.list()`. Downloads missing
     models via `ollama.pull(stream=True)` prior to query stage.
   - Vector Retrieval: Performs cosine similarity search over Qdrant index, retrieving
     top k=4 document chunks inside a Rich spinner block.
   - Hardware Enforcement: Sets `os.environ["OLLAMA_NUM_GPU"] = "0"` if device is CPU to force
     Ollama CPU execution; unsets variable when CUDA device is active.
   - Answer Synthesis: Constructs context string with page attribution (`[Page X]`), sends prompt
     to `ChatOllama`, and displays response using `ui.answer_panel()`.

E. Cleanup & Lifecycle Management (main.py: cleanup_node & main block)
   - LLM Offloading: Invokes `ollama stop <model_name>` via subprocess to immediately un-load the
     model from memory/VRAM, bypassing Ollama's ~5-minute default idle timeout.
   - Database Connection: Explicitly closes Qdrant client lock.
   - Disk Sanitization: Deletes temporary `./qdrant_db` folder via `shutil.rmtree()`.
   - Signal Handling: Executed on normal flow exit (`exit/bye/close`), as well as inside a
     `finally` block on Ctrl+C (`KeyboardInterrupt`).
